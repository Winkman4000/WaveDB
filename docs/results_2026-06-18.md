# WaveDB vs DuckDB — 100M hits (ClickBench), 2026-06-18

Pod: RunPod, 64 GB RAM / 8 vCPU / 180 GB disk. Segment `hits_0.wdb`, N = 99,997,497.
Oracle: DuckDB over the same data. All results **exact-match** the oracle / an independent groupby.
Warm = median of repeated calls (caches primed). Commits: `a1debc5`, `5494b4d`, `3809b83`,
`4aab154`, `44f597d` on `main`.

## Two new query families, wired into db.run

| query | WaveDB compute | WaveDB route_single_segment | DuckDB | correctness |
|---|---|---|---|---|
| `EXTRACT(year/month/day FROM EventDate)`, COUNT(*), GROUP BY | ~2.3 µs (V→G rollup) | ~259 µs | ~4–5 ms | exact |
| 2-key top-10 `UserID, SearchPhrase, COUNT(*) … ORDER BY COUNT(*) DESC LIMIT 10` | µs slice | ~155 µs | ~12 s (scan) | exact |

`route_single_segment` = the query engine's own cost (parse + detect-chain + execute), excluding the
per-call `db.run` catalog/segment-open wrapper (~800–940 µs, uniform across all queries — a separate,
pre-existing overhead, not introduced by these features).

### Speedups (route-level, vs DuckDB)
- date-coarsening COUNT(*): ~17–20×
- 2-key top-10: ~75,000× (vs the ~12 s scan this shape previously required)

## How each works (no new per-query scan)
- **Date coarsening** (`wdb_sql`): a GROUP BY key may be `EXTRACT(unit FROM datecol)`. The unit is
  evaluated over the column's **dictionary** (V values) to give a per-code group value; for the
  single-key COUNT(*) shape the answer is a **V→G rollup over per-code counts** — O(V), no per-row
  pass. The date dictionary already stored *is* the source; no new persisted state. SUM / two-key /
  filtered shapes fall back to the (correct) general computed-key path.
- **Heavypair** (`wdb_heavypair`): the 2-key COUNT(*) top-K is answered from a persisted
  count-descending pair sidecar (`.gbp`, heavy hitters count≥2) as a top-N slice, plus ratio-spaced
  landmarks for threshold/rank shapes. The 2-key generalization of `wdb_gbcount`.

## Honest caveats (kept attached so nothing is oversold)
- Date-coarsening fast path is **single computed key, COUNT(*)-only, filter-free**. Other shapes
  remain correct via the general path but don't get the µs rollup.
- Heavypair **cold build on 100M**: 16.6 s, peak RSS 16.7 GB (one-time; peak scales with rows, not
  with the 161 MB resting sidecar). Fit comfortably on the 64 GB box; on a much smaller box the build
  transient (not the sidecar) would be the limit — chunked build is the lever, not needed here.
- The ~800 µs `db.run` wrapper tax (catalog lookup + segment open + col_map) applies to every query
  and is the next-biggest single lever; left as separate work.

## Cross-dataset check (the point of the 100M run)
Both techniques were developed on 6M TPC-H lineitem and confirmed here on a *different* dataset
(ClickBench hits) with *different* date storage (`EventDate`: mode 0, unit D, V=17 vs `l_shipdate`
V=2526) and a genuinely high-card pair (`UserID` 17.6M × `SearchPhrase` 6M). The day-vs-ns unit bug
the test fixture caught (and the fix) is exactly the single-dataset assumption this run was meant to
flush out. Both held.
