## Notes on non-results (T/O and ERR)

The `T/O` entries fall in two honest buckets, confirmed by warm re-measurement (not cold-build artifacts to be hand-waved away):

- **Genuinely heavy even warm.** e.g. Q17 (`SearchPhrase, COUNT(DISTINCT UserID)`) runs ~19s warm and does not yet match DuckDB's result — a real correctness+speed gap, not a methodology artifact. These stay marked as losses/gaps deliberately.
- **Sidecar-build on first call.** Some 2-key high-card group-bys build a `.gbp` sidecar on first execution; the board's cold-fresh-process harness times out that first build. They run faster on subsequent calls, but several are still slow warm, so we do not claim a win.

The `ERR` entries are **honestly unsupported query shapes** — real unclaimed work, not artifacts:
- positional GROUP BY (`GROUP BY 1`, Q34/Q38)
- arithmetic group keys (`ClientIP - 1`, Q39)
- `REGEXP_REPLACE` group keys (Q28/Q32)
- `CASE`-expression group keys (Q39-class)
- `SELECT *` projection ordering (Q27)

These are candidate targets for future query-shape work.

## scanpair kernel (high-match 2-key COUNT(*) top-K)

The merged AVX-512 native-dtype hash-aggregation kernel with radix-partitioned parallel tally
improves the filtered 2-key COUNT(*) top-K cases vs the prior numpy path (100M, bit-exact):
CounterID=62 (selective) big win; RegionID dominant ~18% 0.84x->1.53x; RegionID 2 ~7% 1.63x->1.78x;
ResolutionWidth dominant ~24% 0.61x->0.76x (still trails DuckDB at this extreme — memory-bandwidth
bound; parallelism saturates at ~4-8 cores). This is the C24/C25 row family above.
